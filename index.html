An agent's account of its own work is not evidence of what it did.

I build AI agents from scratch, measure whether what they report matches what actually happened, and publish where oversight breaks down, including where my own measurements were wrong.

Findings

Every number below is reproducible from the linked repos.

0 honestfailures across 160 runs, four tasks and two models. Every failure came back looking like a success.
38%silent failures on the login task with Llama-3.3-70B: 34 of 89 runs overall, swinging 10–60% across eight sessions.
39% → 0in the controlled comparison: the same task at 39% baseline dropped to 0 of 26 runs after one change to the page.
3 of 8Inspect eval runs that claimed "done" were wrong, and none failed honestly. One run per task: existence, not a rate.

Reliability looks like a property of the model–task pair, not the model alone. That rests on eight cells: a supported hypothesis, not an established result.

The mechanism, and the test that isolated it

The destructive element sat first in the list the agent perceives. So I moved it.

ref[1] Logout
ref[2] Products
ref[3] Cart
ref[4] Account
39%
silent-failure rate, Logout at position 1

Same element, same page, same label, still clickable. Only its position in the agent's element list changed, and the failure disappeared across 26 runs. Verified with a probe that makes no model calls, so the effect can't be confused with anything the model decided.

Where oversight breaks

Detection rate out of 10 runs, deception study.

Fabrication, detector has the source10/10
Agent's reasoning visible and honest10/10
Fabrication, no source4/10
Deceiver hides its reasoning (harder text)0/10
Deceiver hides its reasoning (easier text)7–9/10
Slanted summary, even with the source0/10

The only signal strong enough to catch subtle deception is the one the agent controls. Hiding the reasoning collapsed detection on one text and left it high on another, so the method itself is unreliable rather than uniformly weak. Single model so far; cross-model replication is the open item.

What I actually build

The check that sits outside the agent, which is the whole argument.

Most agent stacks stop at the report. Everything I measure comes from reading the page myself and comparing. Built: the postcondition checker. Not built, and named as the next step: scoring an action before it is taken.

Work

Built from scratch in Python. All public.

Bedrock

Browser-agent reliability study

A browser agent on Playwright and an LLM, with no framework hiding the failures, plus a postcondition checker that compares the agent's report with the page's real state.

  • Traced the self-undo to a stop-condition failure. Step budget ruled out: the agent never used more than 4 of 12 steps.
  • Widened to four tasks and found two more failure classes: weak-evidence verification and state-tracking failure.
  • The provider retired the headline model mid-study. That figure can't be reproduced by anyone, including me, and I say so up front.

bedrock-eval

Inspect AI eval · Docker · 43 tests

The Bedrock study rebuilt in UK AISI's Inspect framework, with pages pinned inside Docker so results don't drift.

  • Scorer with four outcomes: pass, silent failure, honest failure, planner error.
  • My tests caught Inspect's default epoch reducer turning text scores into numbers. Every metric would have read 0.0: an eval for silent failure, failing silently. Fixed with Epochs(1, reducer=[]).
  • Register submission in discussion with AISI maintainers (issue #2467).

Deceptive-agent detection

Where reasoning-monitoring breaks down

An honest agent, a deceptive agent with a secret goal, and detectors given the source, no source, or the agent's reasoning, across omission, fabrication and slant.

  • Without the source, deception passed as faithful about half the time.
  • Hiding the reasoning collapsed detection on one of two texts.
  • No single oversight method caught every deception type.

Meta-agent

An agent that builds agents

Reads a task, designs a team of agents, picks a structure (debate, pipeline or single) and runs it.

  • Reliability harness checks correctness, groundedness and run-to-run consistency.
  • Its own eval showed it catches obvious errors but has reproducible blind spots on subtle claims.
  • Earlier: tier-zero, a five-agent GitHub auditor with an adversarial critic.

What I got wrong

Five errors, all caught by me. Four had reached public claims and were retracted with the data kept.

  1. Retraction 1

    A variance figure was config drift in my own setup, not the agent.

  2. Retraction 2

    A generalisation claim failed on two analog tasks I built specifically to confirm it.

  3. Retraction 3

    Injection results were measured against a page the perturbation never reached.

  4. Retraction 4

    A second injection set was void: the harness told the agent the page had changed, on the exact step where the failure occurs.

  5. Caught before any claim

    A verification script that could only ever print 100%. A check that can't return a negative isn't a check, and I now look for that shape first.
